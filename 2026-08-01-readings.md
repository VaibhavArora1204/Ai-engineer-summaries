## 1. Research Papers

### Challenges and Applications of Large Language Models
📄 **Paper:** [arxiv.org/pdf/2311.04235](https://arxiv.org/pdf/2311.04235)

A comprehensive 2023 survey paper that catalogs the major **challenges** facing LLMs and maps them to real-world **applications**. Key areas covered:

- **Design Challenges:** Tokenization issues (especially for non-English / code), long-context handling, attention complexity (quadratic scaling), and hallucination.
- **Behavioral Challenges:** Faithfulness, bias & toxicity, lack of attribution/citation in generated outputs.
- **Science of LLMs:** Scaling laws, emergent abilities, in-context learning mysteries, prompt sensitivity.
- **Applications Surveyed:** Code generation, reasoning (math, logical), dialogue systems, information extraction, text summarization, machine translation.
- **Key Insight:** LLMs are *not* just bigger language models — they exhibit qualitatively different behaviors at scale (emergent abilities), but they also inherit and amplify training data biases.

> **Why read this:** Gives you the big-picture landscape of what LLMs can and can't do, and where the field's open problems lie. Great for building intuition before diving into implementation.

## 2. Hands-On Build-from-Scratch Repos

### 2a. Llama from Scratch (bkitano)
🔗 [github.com/bkitano/llama-from-scratch](https://github.com/bkitano/llama-from-scratch) — ⭐ 581 stars

**"How to implement a paper without crying."** A practical walkthrough of building a scaled-down Llama model, trained on TinyShakespeare. Inspired by Karpathy's Makemore series.

**Key Lessons:**
1. **Work iteratively:** Start with helper functions (data splits, training loop, loss plotting) before touching the model architecture.
2. **Validate tensor shapes religiously:** Use `.shape`, `assert`, and `plt.imshow` constantly.
3. **Test layers independently** — e.g., RoPE embeddings have testable mathematical properties.
4. **Start with a simple model first** (basic FFN with embeddings), confirm gradients flow, then swap in paper components one-by-one.

**Architecture components implemented:**
- Character-level tokenizer (vs. SentencePiece BPE in real Llama)
- RMSNorm (instead of LayerNorm)
- Rotary Positional Embeddings (RoPE)
- Multi-head attention with KV caching
- SwiGLU activation (instead of ReLU)
- Config-driven architecture for clean code

**Debugging insight:** The guide shows a common bug — using `F.softmax` before `F.cross_entropy` (which already applies softmax internally), resulting in near-zero learning. Cross-entropy loss intuition: `loss = 4.17` means model picks from ~65 tokens randomly; `loss = 1.5` means it's choosing from ~4.5 tokens effectively.

## 3. LLM Training Guide

### The Novice's LLM Training Guide
🔗 [rentry.org/llm-training](https://rentry.org/llm-training)

Written by **Alpin** (AlpinDale). A practical, community-driven guide focused on actually training/fine-tuning LLMs. Uses the **Axolotl trainer**.

**Core Concepts Covered:**

#### Transformer Basics
- LLMs = "lossy text compression" — random tensors learn probability distributions over language
- Pre-training: TB-scale data, learns general language patterns via Causal Language Modeling (predict next token) or Masked Language Modeling
- Fine-tuning: Small task-specific dataset, adjusts pre-trained weights via SGD/Adam

#### LoRA & QLoRA
- **LoRA** reduces trainable params by 10,000x and GPU memory by 3x vs. full fine-tuning
- **QLoRA** adds on-the-fly quantization (via `bitsandbytes`), enabling 70B model training on 2x RTX 3090s (vs. 16x A100-80GB normally)
- Key LoRA hyperparameters:
  - **Rank (r):** Controls capacity. Higher = more expressive but more memory. Start with 8-16.
  - **Alpha (α):** Scaling factor. Common rule: `α = 2 * r`
  - **Target modules:** Which layers to apply LoRA to (q_proj, v_proj, etc.)

#### Training Hyperparameters
- **Batch size:** Number of samples per gradient update
- **Epoch:** One full pass through the dataset
- **Learning Rate:** How big the optimization steps are. Too high = diverge, too low = slow convergence
- **Gradient Accumulation:** Simulate larger batches on limited VRAM by accumulating gradients over multiple forward passes before stepping

#### Dataset Preparation
- **Quality > quantity** (but aim for ≥10 MiB for fine-tunes)
- **Diversity matters** — don't train on only one narrow task
- Parsing tools: BeautifulSoup (HTML), pandas (CSV), sqlparse (SQL)
- Noise minimization is critical

#### Learning Curve Diagnostics
- **Underfit:** Both train and val loss are high and barely decreasing
- **Overfit:** Train loss drops but val loss rises (gap widens)
- **Well-fit:** Both decrease, gap is small and stable

#### Compute Options
- Cloud GPUs: RunPod, VastAI (cheapest), LambdaLabs, AWS SageMaker (most expensive)
- Google TPU Research Cloud: Free program, up to 110 TPU machines (30-day window)
- Memory reference: 7B model fine-tune needs ~160-192GB VRAM

## 12. Social / Viral Threads

### 12a. @irinatoxi (Rina) — Kimi K3 + Blender MCP: AI-Driven 3D Scene Construction
🔗 [x.com/irinatoxi/status/2080550212913725446](https://x.com/irinatoxi/status/2080550212913725446)

A detailed article explaining how **Kimi K3 connected to Blender through MCP** changes the 3D creation workflow — not by generating magic assets, but by **operating Blender directly** as an agent.

#### Key Distinction: This Is Not Text-to-3D
- Kimi K3 does **not** generate a finished 3D file in a chat window
- Through **Kimi Code + MCP servers** (stdio, HTTP, SSE), K3 connects to a running Blender instance
- **BlenderMCP** exposes Blender operations: create objects, change materials, move cameras, manage lights, render previews, inspect scenes, execute Python
- The model operates the **actual Blender project** — not just giving instructions like "select the cube, add a bevel"

#### Why K3 Suits Blender (Most Models Don't)
Blender is unusually hard for AI because the model must:
- Understand 3D space and visual composition
- Track dozens of objects with naming/scene structure
- Interpret screenshots of renders
- Modify Python scripts
- **Remember decisions from many steps earlier**

K3's design advantages for this:
- Long-horizon coding capability
- Native visual understanding ("vision in the loop")
- Tool use via MCP
- 1M token context window
- Can iterate between code and live screenshots

#### The Actual Workflow
1. **Rough blockout:** User describes a scene (e.g., "cinematic cyberpunk street with noodle shop, animated signs, volumetric fog"). K3 creates buildings from cubes, places road, generates shop, adds temp materials, positions lights, sets up camera path
2. **First result looks bad** (guaranteed) — buildings too evenly spaced, shop disappears into background, fog looks like spilled milk
3. **Iterative refinement:** K3 inspects viewport screenshots/renders, compares with the original request, modifies the Blender scene, runs another iteration
4. **The key difference:** K3 is editing **underlying objects, materials, lights, animation curves, and scripts** — not just producing another image

#### Code Is Part of the Workflow
K3 doesn't need a separate MCP command for every operation — it can generate **Blender Python scripts** directly. Example: creating buildings, applying emissive materials, and setting up a neon street in one script execution.

#### Why This Matters
> *"A model that creates a city scene but forgets every previous decision after the next prompt is basically an overcomplicated asset generator. A useful agent needs to preserve the scene, inspect the output, identify problems, and continue making changes without rebuilding everything from scratch."*

This is a practical demonstration of K3's long-context + tool-use + vision-in-the-loop capabilities applied to creative 3D work — not a magic button, but a **tireless assistant that handles the repetitive parts** between first idea and first usable scene.

### 12b. @swill1ams (Sam Williams) — Kimi K3 Deep Technical Architecture Breakdown
🔗 [x.com/swill1ams/status/2082856158520398279](https://x.com/swill1ams/status/2082856158520398279)

An extraordinarily detailed technical thread (article-length) breaking down **Kimi K3**, Moonshot AI's 2.8-trillion-parameter model released July 2026. The thread is essentially a visual explainer of how K3 solves the **KV cache memory problem** that bottlenecks all large-scale LLM serving.

#### The Core Problem: KV Cache Memory
- Every token, at every layer and attention head, stores a small bundle of numbers (keys & values) — the **KV cache**
- This cache grows linearly with context length, leaving less GPU memory for the model itself, fitting fewer users per GPU, and slowing output
- Chinese labs (constrained by US chip export controls) had extra incentive to solve this with **software-based optimizations** rather than scaling hardware

#### The Toolbox: 4 Ways to Fight the Memory Bill

| Strategy | Mechanism | Tradeoff |
|----------|-----------|----------|
| **1. Share (GQA)** | Multiple attention heads share one set of KVs | Industry default (Llama, Qwen, Gemma, Mistral). Removes duplicates but history still grows |
| **2. Shrink (MLA)** | Compress each KV entry into a small latent representation | DeepSeek's approach. ~57× smaller entries (93.3% cache reduction). Still grows per token |
| **3. Forget (Sliding Window)** | Keep only the most recent N tokens, drop the rest | Fixed memory, but exact recall beyond the window is lost. Used by Mistral, Gemma |
| **4. Replace (Linear Attention)** | Replace per-token notebook with a fixed-size state that is edited in place | Memory never grows. Basis of Mamba → DeltaNet → Gated DeltaNet research line |

#### Kimi Delta Attention (KDA) — The K3 Innovation
KDA is a **recurrent state machine** running once per token:
- Carries one fixed-size memory state `S` forward
- **Key and value edit** the state; **query reads** from it
- The updated state becomes the starting point for the next token
- **Contents change; size does not**

**Two key changes from earlier approaches:**
1. **Delta rule (erase, then write):** Instead of blindly adding, KDA fades existing memory, removes the old association for the current key, and writes the new value. A 3-slot whiteboard stays at 3 slots.
2. **128 forgetting dials instead of 1:** Earlier models used one decay rate `α` per head. KDA uses **128 learned α values** (one per channel in the 128-wide state). Names and intent persist; filler disappears. The decay pattern also encodes timing information, replacing the need for separate positional encoding.

#### K3's Hybrid Design: 3:1 KDA to MLA
- **3 out of 4 layers** use KDA (fixed-size state, no memory growth)
- **Every 4th layer** uses Gated MLA (compressed full-recall path for exact retrieval)
- Tested against identical full-attention twin at 48B scale (**Kimi Linear**):
  - **75% less KV cache memory**
  - **Up to 6× more output at 1M tokens** (from serving more users per GPU)
  - **3.98× faster at 128K context**, scored 84.3 on RULER (long-memory benchmark) — higher than the full-attention twin
  - **No measured quality loss** on short tasks, long tasks, or RL

#### Other K3 Architectural Innovations
- **Attention Residuals:** Later layers can look back at earlier layer outputs with learned weights (e.g., 0.6, 0.1, 0.3), instead of reading one blended residual stream
- **Stable LatentMoE:** 896 experts total, but only **16 routed + 2 shared** are active per token → 104B of 2.8T parameters active. Latent projection keeps inter-GPU messages compact
- **Quantile Balancing:** Prevents router from overloading the same experts — calculates per-expert cutoffs from routing scores (no hand-tuned penalty)
- **Per-Head Muon Optimizer:** Updates each attention head independently, preventing one strong head from dominating gradient updates
- **4-bit Quantization-Aware Training:** Trained post-training with 4-bit constraint already in place, so model adapts to it instead of being compressed after the fact

#### Training Recipe (3 Phases)
1. **Pre-training:** Web text, code, math, knowledge, vision data (images + video + text through same backbone)
2. **RL on real work:** Coding, web agents, research, professional knowledge. Episodes run **hundreds to thousands of tool calls**. Trains at multiple thinking effort levels
3. **Distillation:** Separate specialist policies (coding, agent, reasoning) distilled into one unified model

#### Open-Sourced Tooling
- [FlashKDA](https://github.com/MoonshotAI/FlashKDA) — Custom GPU kernels for KDA
- [MoonEP](https://github.com/MoonshotAI/MoonEP) — Expert-communication system for 896 experts during training
- [AgentENV](https://github.com/kvcache-ai/AgentENV) — Resumable sandboxes for long agent runs

#### Pricing & Serving
- Cache miss: **$3/M input tokens**
- Cache hit: **$0.30/M input tokens** (auto-caching, no config needed)
- Output: **$15/M tokens**
- Moonshot reports **>90% cache hit rate** for coding workloads
- A fully cached 1M-token working set costs just **$0.30 to reuse**

#### Key Demonstrations
- [minitriton](https://github.com/MoonshotAI/minitriton) — A compiler (with its own language front end) built entirely by K3
- [nano-kpu](https://github.com/MoonshotAI/nano-kpu) — Register-level hardware for an inference chip, designed by K3

#### Design Philosophy
> *"The pattern is local control. KDA learns decay per channel. Quantile Balancing corrects load per expert. Muon updates attention per head. Rather than trusting one setting to govern a large block, K3 gives smaller parts room to adjust independently."*
