## 1. mattpocock/skills

**Link:** https://github.com/mattpocock/skills  
**Stats:** ⭐ 205k | 🍴 17.7k | 399 commits  
**License:** MIT

### What It Is

A collection of **composable agent skills** (slash-command workflows) for coding agents like Claude Code, Codex, OpenCode, etc. Created by Matt Pocock (TypeScript educator). The philosophy is: *"Skills for Real Engineers. Straight from my `.agents` directory."*

These are **not** a monolithic framework. They are small, hackable, composable files you drop into your project. They address real failure modes of AI-assisted development, grounded in decades of software engineering principles (Domain-Driven Design, Pragmatic Programmer, TDD, etc.).

### Installation — Two Approaches

| Method | What It Does | Updates |
|--------|-------------|---------|
| **Claude Code Plugin** (`claude plugins install mattpocock-skills`) | Read-only managed bundle from official marketplace | Automatic |
| **skills.sh CLI** (`npx skills@latest add mattpocock/skills`) | Copies editable skill files into your repo | Manual (`npx skills update`) |

Do NOT install both — you'd get every skill twice.

After install, run `/setup-matt-pocock-skills` once per repo. It asks:
- Which issue tracker (GitHub, Linear, or local files)
- What labels for triage
- Where to save docs

### Core Philosophy: Four Failure Modes and Their Fixes

#### Failure #1: "The Agent Didn't Do What I Want" — Misalignment

The most common failure in all software development. The fix is a **grilling session** — making the agent ask detailed questions first.

- **`/grill-me`** — For non-code uses. Agent asks you probing questions to align on intent.
- **`/grill-with-docs`** — Same interrogation, but also builds a **shared domain language** (CONTEXT.md) and documents decisions as ADRs.

The shared language (`CONTEXT.md`) is the single most powerful technique. Example:
- BEFORE: *"There's a problem when a lesson inside a section of a course is made 'real' (i.e. given a spot in the file system)"*
- AFTER: *"There's a problem with the materialization cascade"*

Benefits of shared language:
- Variables, functions, files named consistently
- Codebase easier to navigate for the agent
- Agent spends fewer tokens on thinking (more concise concepts)

#### Failure #2: "The Agent Is Way Too Verbose" — No Ubiquitous Language

Agents use 20 words where 1 will do because they're dropped into a project cold. The fix is `/grill-with-docs` which builds that shared vocabulary.

#### Failure #3: "The Code Doesn't Work" — No Feedback Loops

Without feedback on how code actually runs, the agent flies blind.

- **`/tdd`** — Red-green-refactor loop. Agent writes a failing test first, then fixes it. Includes guidance on what makes good/bad tests.
- **`/diagnosing-bugs`** — Wraps best debugging practices into a disciplined loop, gated phase by phase.

#### Failure #4: "We Built a Ball of Mud" — Accelerated Software Entropy

Agents speed up coding → accelerate complexity. The fix: actually care about design.

- **`/to-spec`** — Quizzes you about which modules you're touching before creating a spec.
- **`/improve-codebase-architecture`** — Surveys a codebase for "deepening opportunities" (à la John Ousterhout's *A Philosophy of Software Design*). Produces an HTML report. Run every few days.

### Skill Taxonomy — User-Invoked vs Model-Invoked

**User-invoked** (only you can trigger): orchestration skills.  
**Model-invoked** (agent can call automatically when task fits): reusable discipline.

A user-invoked skill may call model-invoked skills, but never another user-invoked skill.

#### Engineering Skills (User-invoked)

|-------|---------|
| `/ask-matt` | Router — asks which skill fits your situation |
| `/grill-with-docs` | Grilling + builds CONTEXT.md + ADRs |

  -H "Content-Type: application/json" \

**19 routing strategies**, mix and match per combo step:
- `priority`, `fill-first`, `weighted`, `round-robin`, `p2c`, `least-used`, `random`, `strict-random`, `cost-optimized`, `headroom`, `reset-window`, `reset-aware`, `context-relay`, `context-optimized`, `cache-optimized`, `lkgp`, `auto`, `fusion`, `pipeline`

The Auto-Combo engine scores every candidate on **12 factors**: health, quota, cost, latency, success rate, freshness, etc.

### Resilience — 3 Independent Layers

Built-in resilience at three levels (details in `docs/architecture/RESILIENCE_GUIDE.md`).

### Compression — Save 15–95% Tokens

12 composable compression engines including:
- LLMLingua-2
- Two-tier Ultra
- Omniglyph
- Per-step fidelity gate
- GCF v3.2
- RTK (token compression) with language packs for DE, FR, JA, Chinese (wényán)

## 4. Open Code Review

**Link:** https://github.com/alibaba/open-code-review  
**Stats:** ⭐ 19.1k | 🍴 1.3k | 481 commits  
**License:** Apache-2.0

### What It Is

An **AI-powered code review CLI** from Alibaba Group. Battle-tested internally for 2 years, serving tens of thousands of developers and identifying millions of code defects. Now open-source.

It reads Git diffs, sends changed files to a configurable LLM via an **agent with tool-use capabilities**, and generates **structured review comments with line-level precision**. The agent can read full file contents, search the codebase, inspect other changed files for context.

### Benchmark Results (vs General-Purpose Agents)

Benchmarked on 50 popular open-source repos, 200 real PRs, 10 programming languages, cross-validated by 80+ senior engineers (1,505 annotated ground-truth issues):

- **Higher Precision and F1** than Claude Code with the same underlying model
- **~1/9 of the tokens** consumed
- **Faster** review completion
- **Lower Recall** — deliberate trade-off favoring precision over noise

### Why Not Just Use Claude Code with Skills?

Three pain points of general-purpose agents for code review:
1. **Incomplete coverage** — On larger changesets, agents "cut corners," selectively reviewing only some files
2. **Position drift** — Reported issues frequently don't match actual code location (line numbers drift)
3. **Unstable quality** — Natural-language-driven Skills are hard to debug, quality fluctuates with minor prompt variations

**Root cause:** A purely language-driven architecture lacks **hard constraints** on the review process.

### Core Architecture: Deterministic Engineering × Agent Hybrid

**Deterministic Engineering** (hard constraints — engineering logic guarantees correctness):
- **Precise file selection** — Determines exactly which files need review, which are filtered
- **Smart file bundling** — Groups related files into a single review unit (e.g., `message_en.properties` and `message_zh.properties` bundled together). Each bundle runs as a **sub-agent with isolated context** — divide-and-conquer that stays stable on very large changesets and supports concurrent review
- **Fine-grained rule matching** — Matches review rules to each file's characteristics via template-engine-based matching (more stable than purely language-driven guidance)
- **External positioning and reflection modules** — Independent modules that systematically improve location accuracy and content accuracy of AI feedback

**Agent** (dynamic decisions):
- **Scenario-tuned prompts** — Deeply optimized for code review (not generic)
- **Scenario-tuned toolset** — Distilled from analysis of tool-call traces in large-scale production data: call frequency distributions, per-tool repetition rates, impact of new tools on overall call chain

### Built-in Rule Categories

Multi-language ruleset covering:
- **NPE** (Null Pointer Exceptions)
- **Thread-safety** issues
- **XSS** vulnerabilities
- **SQL injection**
- OpenAI & Anthropic API compatible

### Usage

```bash
# Install
npm install -g @alibaba-group/open-code-review

# Configure LLM
ocr config provider
ocr config model

# Review modes
ocr review                                          # All staged/unstaged/untracked changes
ocr review --from main --to feature-branch          # Branch range
ocr review --commit abc123                          # Single commit
ocr scan                                            # Full-file scan (no git history needed)
ocr scan --path internal/agent                      # Scan directory or files

# Delegation mode — let your AI coding agent perform the review itself
ocr delegate preview
ocr delegate rule src/main.go src/handler.go
```

## 11. Inside vLLM: Anatomy of a High-Throughput LLM Inference System

**Link:** https://www.aleksagordic.com/blog/vllm  
**Author:** Aleksa Gordić  
**Date:** August 29, 2025  
**Based on:** vLLM commit `42172ad` (August 9, 2025), V1 engine

### Overview

A deep, code-level breakdown of how vLLM works. Structured as an inverse pyramid — starts broad, layers in detail. Five parts:

1. **LLM Engine & Engine Core** — fundamentals (scheduling, paged attention, continuous batching)
2. **Advanced Features** — chunked prefill, prefix caching, guided & speculative decoding, disaggregated P/D
3. **Scaling Up** — single-GPU to multi-GPU execution
4. **Serving Layer** — distributed/concurrent web scaffolding
5. **Benchmarks and Auto-tuning** — measuring latency and throughput

---

### Part 1: LLM Engine & Engine Core

#### Engine Constructor — Main Components

```
LLM Engine
├── vLLM Config (all knobs: model, cache, parallelism, etc.)
├── Processor (raw inputs → EngineCoreRequests via validation, tokenization)
├── Engine Core Client
│   └── InprocClient (synchronous single-process)
│   └── DPLBAsyncMPClient (distributed serving at scale)
├── Output Processor (EngineCoreOutputs → RequestOutput)
└── Engine Core
    ├── Model Executor
    │   └── UniProcExecutor (single GPU, single Worker)
    │   └── MultiProcExecutor (multiple GPUs)
    ├── Structured Output Manager (guided decoding)
    └── Scheduler
        ├── Policy: FCFS or Priority
        ├── waiting queue + running queue
        └── KV Cache Manager
            └── free_block_queue (pool of available KV-cache blocks)
```

#### KV-Cache Block Size Formula

For a standard transformer layer (non-MLA):

```
block_size_bytes = 2 (key/value) × block_size (default=16 tokens) × num_kv_heads × head_size × dtype_bytes (e.g. 2 for bf16)
```

#### Worker Initialization (3 Key Steps)

**1. Init Device:**
- Assign CUDA device (e.g., `cuda:0`) to worker
- Verify dtype support (e.g., bf16)
- Check VRAM availability against `gpu_memory_utilization` (default 0.8 = 80%)
- Set up distributed settings (DP/TP/PP/EP)
- Instantiate `model_runner` (holds sampler, KV cache, forward-pass buffers: `input_ids`, `positions`, etc.)
- Instantiate `InputBatch` (CPU-side buffers, block tables for KV-cache indexing, sampling metadata)

**2. Load Model:**
- Instantiate model architecture
- Load weights
- `model.eval()` (PyTorch inference mode)
- Optional: `torch.compile()` on the model

**3. Initialize KV Cache:**
- Get per-layer KV-cache spec (`FullAttentionSpec` for homogeneous transformers; hybrid specs for sliding window / Transformer+SSM like Jamba — see Jenga)
- Run dummy/profiling forward pass → GPU memory snapshot → compute how many KV cache blocks fit in available VRAM
- Allocate, reshape, bind KV cache tensors to attention layers
- Prepare attention metadata (e.g., FlashAttention backend)
- Unless `--enforce-eager`: for each warmup batch size, capture **CUDA Graphs** (record GPU work into a DAG for replaying, cutting kernel launch overhead)

#### Generate Function — Request Processing

For each prompt:
1. Create unique request ID + capture arrival time
2. Input preprocessor tokenizes prompt → `{prompt, prompt_token_ids, type}`
3. Pack into `EngineCoreRequest` with priority, sampling params
4. Engine core wraps in `Request` object, sets status to `WAITING`, adds to scheduler's `waiting` queue

#### Engine Loop — Three Stages Per Step

```
while requests_to_process:
    1. SCHEDULE — select which requests to run (decode and/or prefill)
    2. FORWARD PASS — run model, sample tokens
    3. POSTPROCESS — append sampled token IDs, detokenize, check stop conditions
```

**Stop conditions:**
- Exceeds `max_model_length` or its own `max_tokens`
- Sampled token is EOS ID (unless `ignore_eos` enabled — useful for benchmarking)
- Sampled token matches any `stop_token_ids`
- Stop strings found in output (output truncated at first stop string appearance)

#### Scheduler — Prefill vs Decode

Two workload types:

| Workload | Description | Bound |
|----------|-------------|-------|
| **Prefill** | Forward pass over ALL prompt tokens. Sample one token from final position. | **Compute-bound** (threshold depends on hardware + prompt length) |
| **Decode** | Forward pass over just the most recent token. All earlier KVs cached. Still loads all LLM weights + KV caches for one token. | **Memory-bandwidth-bound** |

V1 scheduler can **mix both types** in the same step (V0 could only do one at a time).

Scheduling priority: **Decode first** (already running requests), then Prefill (waiting requests).

For each decode request:
1. Compute number of new tokens (not always 1 — speculative decoding, async scheduling)
2. Call `kv_cache_manager.allocate_slots`
3. Update token budget

For each prefill request:
1. Get number of computed blocks (0 if no prefix caching)
2. Call `kv_cache_manager.allocate_slots`
3. Pop from `waiting`, move to `running`, status → `RUNNING`
4. Update token budget

#### allocate_slots — What Happens

1. **Compute number of blocks** — `ceil(new_tokens / block_size)`. E.g., 17 tokens → `ceil(17/16) = 2` blocks
2. **Check availability** — If not enough blocks in pool:
   - Decode: may attempt **recompute preemption** (evict low-priority requests, free their KV blocks)
   - Prefill: may skip scheduling
3. **Allocate blocks** — Fetch first `n` blocks from `free_block_queue` (doubly linked list). Store in `req_to_blocks[request_id]`

#### Forward Pass — Continuous Batching + Paged Attention

1. **Update states** — Prune finished requests from `input_batch`, update KV cache block metadata
2. **Prepare inputs** — CPU→GPU buffer copy, compute positions, build `slot_mapping`, construct attention metadata
3. **Forward pass** — All sequences **flattened and concatenated** into one "super sequence." Position indices + attention masks ensure each sequence only attends to its own tokens. This enables continuous batching **without right-padding.**
4. **Gather last-token states** — Extract hidden states for each sequence's final position → compute logits
5. **Sample** — From logits: greedy, temperature, top-p, top-k, etc.

Two execution modes:
- **Eager mode** — Standard PyTorch forward pass
- **Captured mode** — Execute/replay pre-captured CUDA Graph (cuts kernel launch overhead)

---

### Part 2: Advanced Features

#### Chunked Prefill

**Problem:** A single very long prompt monopolizes one engine step, postponing all other requests.

**Solution:** Cap number of new tokens per step. If requested exceeds `long_prefill_token_threshold`, reset to that value. A long prompt `P` split into chunks `x-y-z` (e.g., 8 tokens each, with `z` being an incomplete final chunk) would take ≥3 engine steps, sampling only on the last chunked step.

Enable: set `long_prefill_token_threshold` to a positive integer. Can also happen implicitly if prompt length exceeds token budget.

#### Prefix Caching

**Problem:** Multiple prompts sharing the same prefix recompute the same KV cache.

**Solution:** Hash completed KV-cache blocks and store them. When a new request has matching prefix hashes, reuse those blocks directly — only compute the new suffix tokens.

**Mechanism:**

1. Split `long_prefix + prompt` into 16-token chunks
2. For each complete chunk: compute hash (combining previous block's hash + current tokens + optional metadata: MM hash, LoRA ID, cache salt)
3. Store as `BlockHash` objects in `req_to_block_hashes[request_id]`
4. On first request: no hits in `cached_block_hash_to_block`
5. After allocation + forward pass: `coordinator.cache_blocks` associates `BlockHash` entries with allocated KV blocks, records in `cached_block_hash_to_block`
6. On second request with same prefix: `find_longest_cache_hit` finds all matching blocks via linear search. Reuse directly.

**Block invalidation:** Blocks become invalid only when about to be reallocated from `free_block_queue` — at that moment, clear hash and remove from cache map.

Prefix caching is **enabled by default**. Disable: `enable_prefix_caching = False`.

**Key insight:** If you understand prefix caching, you also understand paged attention.

#### Guided Decoding (FSM — Finite State Machine)

At each decoding step, logits are constrained by a grammar-based FSM. Only tokens allowed by the grammar can be sampled.

Supports:
- **Regular grammars** (Chomsky type-3) — arbitrary regex patterns
- **Context-free grammars** (type-2) — covers most programming languages

Example: `GuidedDecodingParams(choice=["Positive", "Negative"])` forces output to be exactly one of those strings.

**How it works internally:**
- A grammar (regex, JSON schema, BNF, etc.) is compiled into an FSM
- Each state has a set of allowed token IDs (the "bitmask")
- At each decode step, the bitmask is applied to logits (disallowed tokens get -inf)
- The FSM advances state based on the sampled token

The FSM compilation happens once per unique grammar. Multiple requests sharing the same grammar share the same compiled FSM but track independent state positions.

#### Speculative Decoding

**Problem:** Decode is memory-bandwidth-bound — loading all weights to produce one token is wasteful.

**Solution:** Use a small **draft model** to speculate multiple tokens ahead, then **verify** them all at once with the main model in a single forward pass.

**Steps:**
1. Draft model generates `k` candidate tokens autoregressively (fast — small model)
2. Main model runs a single forward pass over all `k` tokens simultaneously
3. Compare draft tokens with main model's distribution
4. Accept matching tokens, reject where they diverge
5. Resample from the first rejected position

**Key property:** Produces **exactly the same output distribution** as running the main model alone — it's a lossless speedup.

Speedup depends on **acceptance rate** — how often the draft model agrees with the main model. Higher agreement = more tokens verified per step = faster.

#### Disaggregated Prefill/Decode (P/D)

**Problem:** Prefill (compute-bound) and Decode (memory-bandwidth-bound) have fundamentally different hardware utilization profiles. Mixing them on the same GPU wastes resources.

**Solution:** Run prefill on one set of GPUs and decode on another. After prefill completes, transfer the KV cache to the decode cluster.

**Implementation in vLLM** (using `SharedStorageConnector`):

1. **Instantiation** — During engine construction, connectors are created in two places: inside the worker's init device procedure (role "worker") and inside the scheduler constructor (role "scheduler")
2. **Cache lookup** — When the scheduler processes prefill requests from the `waiting` queue, it calls `connector.get_num_new_matched_tokens` to check for externally cached tokens. Prefill always sees 0; decode may have a cache hit.
3. **State update** — `connector.update_state_after_alloc` records requests that had a cache hit (no-op for prefill)
4. **Meta build** — `connector.build_connector_meta`:
   - Prefill adds all requests with `is_store=True` (to upload KV)
   - Decode adds requests with `is_store=False` (to fetch KV)
5. **Context manager** — Before the forward pass:
   - On enter: `kv_connector.start_load_kv` — For decode, loads KV from external server into paged memory. For prefill, no-op.
   - On exit: `kv_connector.wait_for_save` — For prefill, blocks until KV is uploaded. For decode, no-op.

**Additional details:**
- For `SharedStorageConnector`, "external server" is just a local file system
- KV transfers can be done layer-by-layer (before/after each attention layer) depending on configuration
- Decode loads external KV only once (first step), then computes/stores locally

This allows:
- **Prefill GPUs:** Optimized for compute throughput (high batch sizes, fully utilized FLOPs)
- **Decode GPUs:** Optimized for memory bandwidth (maximize tokens/second at low arithmetic intensity)

### Part 3: Scaling Up — From UniProcExecutor to MultiProcExecutor

When model weights no longer fit in a single GPU's VRAM, you shard across GPUs.

**Parallelism strategies:**

| Strategy | What It Does | When to Use |
|----------|-------------|-------------|
| **Tensor Parallelism (TP)** | Splits weights within each layer across GPUs on the same node | First choice — intranode bandwidth is much higher |
| **Pipeline Parallelism (PP)** | Splits layers across nodes (GPU 0 → layers 0-15, GPU 1 → layers 16-31) | When model won't fit on a single node |
| **Expert Parallelism (EP)** | Distributes MoE experts across GPUs | MoE models only |
| **Data Parallelism (DP)** | Replicates the entire model, processes different requests on different replicas | Scaling throughput |

**How MultiProcExecutor works in vLLM:**

1. Initializes an `rpc_broadcast_mq` message queue (implemented with shared memory)
2. Loops over `world_size` (e.g., `TP=8 ⇒ world_size=8`) and spawns a daemon process for each rank via `WorkerProc.make_worker_process`
3. For each worker, parent creates reader and writer pipes
4. New process runs `WorkerProc.worker_main` — instantiates a worker going through the same "init device", "load model", etc. as `UniProcExecutor`
5. Each worker determines if it's the driver (rank 0 in TP group) or regular. Every worker sets up two queues:
   - `rpc_broadcast_mq` (shared with parent) for receiving work
   - `worker_response_mq` for sending responses back
6. Each child sends its `worker_response_mq` handle to parent via pipe. Once all received, parent unblocks — coordination complete
7. Workers enter busy loop, blocking on `rpc_broadcast_mq.dequeue`. When work arrives, they execute it (with TP/PP-specific partitioned work). Results sent back through `worker_response_mq.enqueue`
8. At runtime, `MultiProcExecutor` enqueues into `rpc_broadcast_mq` (non-blocking) for all workers, then waits on the designated output rank's `worker_response_mq.dequeue` for the final result

**From the engine's perspective, nothing changes** — all multiprocessing complexity is hidden behind `model_executor.execute_model`.

### Part 4: Serving Layer — Distributed System

#### Example Setup: Two H100 Nodes, Four vLLM Engines

Model requires `TP=4`, each node has 8 GPUs → 2 engines per node, `DP=4` total.

**Node 1 (Headless — no API server):**

```bash
vllm serve <model-name> \
  --tensor-parallel-size 4 \
  --data-parallel-size 4 \
  --data-parallel-size-local 2 \
  --data-parallel-start-rank 0 \
  --data-parallel-address <master-ip> \
  --data-parallel-rpc-port 13345 \
  --headless
```

**Node 2 (API server):** Same command, but `--data-parallel-start-rank 2` and no `--headless`.

#### On the Headless Node

A `CoreEngineProcManager` launches 2 processes (per `--data-parallel-size-local`), each running `EngineCoreProc.run_engine_core`. Each creates a `DPEngineCoreProc` (the engine core) then enters its busy loop.

`DPEngineCoreProc` initialization:
1. Creates `input_queue` and `output_queue` (`queue.Queue`)
2. Performs initial handshake with frontend on the other node using a `DEALER` ZMQ socket, receives coordination address info
3. Initializes DP group (e.g., using NCCL backend)
4. Initializes `EngineCore` with `MultiProcExecutor` (TP=4 on 4 GPUs)
5. Creates a `ready_event` (`threading.Event`)
6. Starts input daemon thread running `process_input_sockets(…, ready_event)` and output thread
7. Main thread waits on `ready_event` until all input threads across all 4 processes (spanning 2 nodes) complete coordination handshake
8. Once unblocked, sends "ready" message to frontend with metadata (e.g., `num_gpu_blocks`)
9. All three threads (main, input, output) enter their busy loops

**Result:** 4 child processes (one per DP replica), each running main + input + output thread.

**Steady state:**
- **Input thread** — blocks on input socket until request routed from API server; decodes payload, enqueues via `input_queue.put_nowait(...)`
- **Main thread** — wakes on `input_queue.get(...)`, feeds request to engine; `MultiProcExecutor` runs forward pass, enqueues results to `output_queue`
- **Output thread** — wakes on `output_queue.get(...)`, sends result back through output socket

**Additional mechanics:**
- **DP wave counter** — tracks "waves"; counter increments when new work arrives after all engines become idle
- **Control messages** — API server can send aborts and utility/control RPCs
- **Dummy steps for lockstep** — if any DP replica has work, ALL replicas execute a forward step; replicas without requests do a dummy step to participate in synchronization points. (Required for MoE models where expert layers form EP/TP group while attention layers are still DP. Currently always done with DP.)

#### On the API Server Node

Instantiates `AsyncLLM` (asyncio wrapper around the LLM engine), which creates `DPLBAsyncMPClient` (data-parallel, load-balancing, asynchronous, multiprocessing client).

Inside `MPClient`, `launch_core_engines`:
1. Creates ZMQ addresses for startup handshake
2. Spawns a `DPCoordinator` process
3. Creates a `CoreEngineProcManager` (same as headless node)

Inside `AsyncMPClient`:
1. Creates `outputs_queue` (`asyncio.Queue`)
2. Asyncio task `process_outputs_socket` communicates with output threads of all 4 `DPEngineCoreProc`, writes into `outputs_queue`
3. Another asyncio task `output_handler` from `AsyncLLM` reads from this queue and sends info to `create_completion`

Inside `DPAsyncMPClient`: asyncio task `run_engine_stats_update_task` communicates with DP coordinator.

**DP Coordinator** mediates between frontend (API server) and backend (engine cores):
- Periodically sends load-balancing info (queue sizes, waiting/running requests) to frontend
- Handles `SCALE_ELASTIC_EP` commands (dynamic scaling with Ray backend)
- Sends `START_DP_WAVE` events to backend, reports wave-state updates back

**Frontend asyncio tasks:**
- Input tasks: each new client request spawns a new asyncio task through `generate` path
- Two output tasks: `process_outputs_socket` + `output_handler`
- One stats task: `run_engine_stats_update_task` for DP coordinator communication

**Load balancing formula:** `score = len(waiting) * 4 + len(running)` — picks engine with minimal score.

#### Full Request Lifecycle

```bash
curl -X POST http://localhost:8000/v1/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "TinyLlama/TinyLlama-1.1B-Chat-v1.0", "prompt": "The capital of France is", "max_tokens": 50}'
```

1. Request hits `OpenAIServingCompletion.create_completion` on the API server
2. Tokenizes prompt asynchronously, prepares metadata (request ID, sampling params, timestamp)
3. Calls `AsyncLLM.generate` → `DPAsyncMPClient.add_request_async`
4. `get_core_engine_for_request` does load balancing across engines
5. `ADD` request sent to chosen engine's `input_socket`
6. At that engine:
   - Input thread unblocks, decodes data, places work item on `input_queue`
   - Main thread unblocks, adds request to engine, repeatedly calls `engine_core.step()`, enqueueing results to `output_queue`
   - Output thread sends results back through output socket
7. Results trigger `AsyncLLM` output tasks, which propagate tokens back to `create_completion`
8. FastAPI attaches metadata (finish reason, logprobs, usage) and returns `JSONResponse` via Uvicorn

**Additional notes:**
- Adding more API servers: load balancing handled at OS/socket level — application doesn't change
- With Ray as DP backend: `/scale_elastic_ep` endpoint enables automatic engine replica scaling

### Part 5: Benchmarks and Auto-tuning

#### Two Competing Metrics

| Metric | Matters For | Description |
|--------|------------|-------------|
| **Latency** | Interactive applications (users waiting) | Time from request submission until tokens returned |
| **Throughput** | Offline workloads (data generation, batch inference) | Tokens/requests per second |

#### Detailed Latency Metrics

| Metric | Definition |
|--------|-----------|
| **TTFT** (Time to First Token) | Time from request submission until first output token received |
| **ITL** (Inter-Token Latency) | Time between two consecutive tokens (token i-1 → token i) |
| **TPOT** (Time Per Output Token) | Average ITL across all output tokens in a request |
| **Latency / E2E** (End-to-End) | Total time = TTFT + sum of all ITLs |
| **Throughput** | Total tokens processed per second (input, output, or both) |
| **Goodput** | Throughput that meets SLOs (max TTFT, TPOT, or E2E latency). Only tokens from requests meeting SLOs are counted |

#### Why Latency and Throughput Compete — The Roofline Model

The tradeoff becomes clear when looking at how batch size `B` affects a single decode step:

- As `B ↓` toward 1: ITL drops (less work per step, no "competition" between tokens)
- As `B ↑`: ITL rises (more FLOPs per step) — but throughput improves because weight I/O is amortized across more tokens

**The roofline model explains this:**
- **Below saturation batch `B_sat`**: Step time dominated by HBM bandwidth (streaming weights layer-by-layer into on-chip memory). Step latency nearly flat — computing 1 vs 10 tokens takes similar time.
- **Above `B_sat`**: Kernels become compute-bound. Step time grows roughly with `B`. Each extra token adds to ITL.

**Formal model:** Step latency = `FLOPs_step / P_kernel`, where `P_kernel` is the achieved performance. As `P_kernel` hits `P_peak`, more compute per step directly increases latency. Kernel auto-tuning can change `P_kernel` as `B` grows (runtime may switch to more efficient kernels for that shape).

#### Benchmarking Scripts in vLLM

vLLM provides `vllm bench {serve,latency,throughput}` CLI:

| Script | What It Does |
|--------|-------------|
| **`latency`** | Short input (32 tokens), 128 output tokens, small batch (8). Multiple iterations, reports E2E latency for the batch |
| **`throughput`** | Fixed set of prompts (1000 ShareGPT samples) all at once (QPS=Inf mode). Reports input/output/total tokens and requests per second |
| **`serve`** | Launches vLLM server, simulates real-world workload with Poisson (or Gamma) inter-arrival times. Sends requests over time window, measures all metrics. Optional max concurrency via semaphore |

```bash
# Example: latency benchmark
vllm bench latency \
  --model <model-name> \
  --input-tokens 32 \
  --output-tokens 128 \
  --batch-size 8
```

Benchmark configs used in CI live under `.buildkite/nightly-benchmarks/tests`.

There is also an **auto-tune script** that sweeps configuration parameters and finds optimal settings for a given hardware + model + workload combination.

## 12. Transformers for Applied Mathematicians

**Paper:** ArXiv 2604.00965  
**Title:** *Understanding Transformers and Attention Mechanisms: An Introduction for Applied Mathematicians*  
**Author:** Michel Fabrice Serret (Paul Scherrer Institute, Switzerland)  
**Date:** April 2026  
**Context:** Written for an IPAM workshop on Randomized Numerical Linear Algebra (RNLA)

### What This Paper Is

A rigorous mathematical introduction to the Transformer architecture, aimed at the applied mathematics community. It starts from first principles (tokenization, embeddings) and builds up to the most modern attention optimization: **Multi-Headed Latent Attention (MLA)** as used in DeepSeek V2.

### Section 1: Tokenization and Embeddings

Given an ordered vocabulary `T = (Tᵢ)` of `N_T` possible tokens, text is decomposed into a sequence of token indices. An embedding matrix `E ∈ ℝ^{N_T × d}` maps each token index to a `d`-dimensional vector.

**Scale reference:**

| Model | Vocabulary Size | Embedding Dimension |
|-------|----------------|-------------------|
| Llama 3 70B | ~128k | 8,192 |
| Gemma 3 27B | ~262k | 5,376 |

Positional embeddings (e.g., RoPE) or feature embeddings enrich the vectors with order information. Some models (DeBERTa, DeepSeek V2) treat positional encoding and token embedding separately through concatenation.

### Section 2: Attention Mechanism

#### General Attention (Single Head)

Given:
- Query input `X_Q ∈ ℝ^{N_Q × d_in}`
- Key input `X_K ∈ ℝ^{N_KV × d_in}`
- Value input `X_V ∈ ℝ^{N_KV × d_in}`

With learned weight matrices:
- `W_Q ∈ ℝ^{d_in × d_QK}`, `W_K ∈ ℝ^{d_in × d_QK}`, `W_V ∈ ℝ^{d_in × d_out}`

The embeddings are:
```
Q = X_Q · W_Q ∈ ℝ^{N_Q × d_QK}
K = X_K · W_K ∈ ℝ^{N_KV × d_QK}
V = X_V · W_V ∈ ℝ^{N_KV × d_out}
```

Attention scores via kernel `κ`:
```
A[i,j] = κ(Q[i,:], K[j,:])      for all (i,j) ∈ [1,N_Q] × [1,N_KV]
```

Normalization: `Z[i,i] = Σⱼ κ(Q[i,:], K[j,:])`

Output: `Y = Z⁻¹ · A · V ∈ ℝ^{N_Q × d_out}`

The kernel is typically softmax: `κ(v,w) = exp(⟨v,w⟩ / √d_QK)`.

#### Multi-Headed Attention (MHA)

Stack `N_heads` parallel attention heads, each with shared `d_head` output dimension.

For head `h`:
```
Q_h = X_Q · W_Q_h,    K_h = X_K · W_K_h,    V_h = X_V · W_V_h
Y_h = Z_h⁻¹ · A_h · V_h ∈ ℝ^{N_Q × d_head}
```

Combined output: `Y = concat(Y₁, ..., Y_{N_heads}) · W_O`

where `W_O ∈ ℝ^{N_heads·d_head × d_out}`.

### Section 3: Transformer Architecture

#### Encoder Layer Components
1. **Multi-headed self-attention** — `X_Q = X_K = X_V` (all from same input)
2. **Layer normalization** — `y = γ ⊙ x̃ + β` where `x̃ = (x - μ)/σ`, with learnable gain `γ` and shift `β`
3. **Feed-forward sublayer** — `y = f(Wx + b)` with nonlinear activation (GLU variants favored in modern models)
4. **Skip connections** — Add sublayer input to its output (preserves information flow, reduces vanishing gradients)

#### Decoder Layers: Two Key Differences

**1. Masked/Causal Attention:** Each query can only attend to itself and preceding tokens:
```
A[i,j] = 𝟙_{j≤i} · κ(Q[i,:], K[j,:])
```
This prevents information leakage from future tokens during autoregressive generation.

**2. Cross-Attention:** Decoder uses encoder's output as key/value inputs, allowing it to relate its generation to the original input.

#### Architecture Variants
- **Encoder-only** (BERT): Bidirectional, suited for classification/extraction tasks
- **Decoder-only** (GPT): Causal, suited for generative tasks (next-token prediction)
- Current trend: Pretrain on massive data (next-token prediction or masked completion), then fine-tune with task-specific heads

### Section 4: KV Caching, Compression, and Attention Optimization

#### The KV Cache Problem

During autoregressive generation, computing the next token requires all prior key and value vectors. Without caching:
- Recompute cost: `O(N³_tokens · d)` — recompute everything for each new token

With KV caching (store K, V after each call):
- Per-token cost: `O(N_Q · N_tokens · d)` — only new queries need computing
- **Memory cost:** `2 · N_L · N_h · N_KV · d` floats per cache

This grows linearly with sequence length and quickly becomes prohibitive for long contexts.

#### Grouped Query Attention (GQA)

Share the same key-value heads across multiple query heads, reducing KV cache size proportionally.

**Spectrum:**
- MHA: `N_KV_heads = N_Q_heads` (no sharing)
- GQA: `N_KV_heads < N_Q_heads` (partial sharing)
- MQA: `N_KV_heads = 1` (single KV head shared by all queries)

#### Multi-Headed Latent Attention (MLA) — DeepSeek V2

**Core idea:** Instead of caching separate K and V matrices for each head, construct a **shared low-rank latent embedding** from which K and V are derived.

**Formulation:**

Standard MHA caches `K` and `V` separately per head. MLA introduces:
```
Latent embedding: L = X · W_L ∈ ℝ^{N_KV × d_L}     (shared across all heads)
```

Where `W_L ∈ ℝ^{d_in × d_L}` and `d_L ≪ d_in`.

The key and value matrices are derived from L via per-head projections:
```
K_h = L · W_LK_h        (latent-to-key, per head)
V_h = L · W_LV_h        (latent-to-value, per head)
```

Similarly for queries:
```
L_Q = X_Q · W_LQ ∈ ℝ^{N_Q × d_LQ}     (latent query embedding)
Q_h = L_Q · W_LQQ_h                      (latent-to-query, per head)
```

**The key optimization — weight merging:**

**Merge 1 (Query × Key):** Since `Q_h · K_h^T = L_Q · W_LQQ_h · W_LK_h^T · L^T`, we can precompute a merged tensor:
```
W_LQK_h = W_LQQ_h · W_LK_h^T ∈ ℝ^{d_LQ × d_L}
```
giving the merged tensor `W_LQK ∈ ℝ^{d_LQ × d_L × N_heads}`.

**Merge 2 (Value × Output):** The final output combines value projections with the output matrix `W_O`:
```
Y = concat(Z_h⁻¹ · A_h · L) · W_LO
```
where `W_LO ∈ ℝ^{N_heads·d_L × d_out}` is the merged latent output matrix.

**Result:** Only need to cache `L` (the shared latent vector, dimension `d_L` per token) instead of separate K and V per head. The only model weights needed are `W_LO`, `W_L`, `W_LQ`, and `W_LQK`.

**Memory comparison:**

| Attention Type | KV Cache Size Per Token | Stored Weights |
|---------------|------------------------|----------------|
| MHA | `2 × N_heads × d_head` | `W_Q`, `W_K`, `W_V`, `W_O` per head |
| GQA | `2 × N_KV_heads × d_head` | Same, but fewer K/V weight sets |
| MLA | `d_L` (shared) | `W_L`, `W_LQ`, `W_LQK`, `W_LO` |

**Concrete model specifications:**

| Parameter | Llama 3 70B | Gemma 3 27B | DeepSeek V2 |
|-----------|-------------|-------------|-------------|
| Layers | 80 | 62 | 60 |
| Attention Heads | 64 | 32 | 128 |
| KV Heads | 8 (GQA) | 16 (GQA) | — (MLA) |
| Hidden Dim (d_in = d_out) | 8,192 | 5,376 | 5,120 |
| Head/KV Dim | 128 | 128 | 512 (d_L) |

DeepSeek V2 is a MoE model with MLA — despite having 128 attention heads, it caches only a 512-dimensional latent vector per token per layer, far less than what GQA would require.

## 13. NVIDIA OO-Agents

**Paper:** ArXiv 2607.20709  
**Repo:** https://github.com/nvidia-nemo/labs-OO-Agents  
**Stats:** ⭐ 856 | 🍴 124 | 169 commits

### The Paper: Core Concept — "Agent as a Python Object"

Traditional agent frameworks scatter logic across: prompt templates, tool schemas, callback code, workflow graphs. **NOOA** (NVIDIA Object-Oriented Agents) collapses all of this into a single Python class:

```python
from nooa import Agent

class SupportAgent(Agent):
    """You are a support agent."""  # ← docstring IS the prompt

    order_db: OrderDB  # ← field IS state (typed)

    def is_refund_eligible(self, order: Order) -> bool:  # ← real body = deterministic Python
        return order.delivered and order.days_since_delivery <= 30

    async def triage(self, message: str, order: Order) -> Ticket:  # ← ... body = LLM-driven
        """Create a typed support ticket."""
        ...
```

**The `...` convention:**
- Methods with `...` bodies = **agentic methods** — implemented at runtime by an LLM-driven strategy
- Methods with real code bodies = **deterministic Python** — standard execution

### Mapping: Traditional Concepts → Python

| Traditional | NOOA Equivalent |
|-------------|----------------|
| System prompt | Class docstring |
| Agent state | Class fields (typed) |
| Tools | Methods with real bodies (via `self`) |
| Tool schemas | Type annotations |
| Agentic actions | Methods with `...` bodies |
| Prompt templates | Method docstrings |
| Typed I/O contracts | Return type annotations |

### Six Key Model-Facing Capabilities

The paper identifies six ideas that NOOA uniquely integrates into a single surface. **No prior framework combines all six:**

#### 1. Typed Input/Output
Python's type system for validated communication. Generation-method arguments are validated on every call. The default CodeAct strategy requires return annotations and validates returned values — with validation errors fed back to the model for retry.

#### 2. Pass-by-Reference
Live Python objects (not serialized text) as arguments. Every call begins with an input-inspection step that prints each parameter's type and a size-bounded preview. The live variable remains in the session for further exploration. This keeps context usage small and under the agent's control — allows processing of large inputs by shape without the full content ever entering the context window.

**Contrast with most frameworks:** Inputs are serialized to text, tool call inputs generated as text by the LLM, outputs returned as text, then parsed back into the host language (full round-trip serialization at every interface).

#### 3. Code as Action
Model writes Python in a Jupyter-style REPL with access to `self`, imports, and helpers. No need for separate tool-schema definitions.

```python
# Traditional: Model calls a tool via JSON schema
{"tool": "search_orders", "arguments": {"customer_id": "123"}}

# NOOA: Model writes Python
result = self.order_db.search(customer_id="123")
if result.is_refund_eligible():
    self.issue_refund(result)
```

This is more expressive (loops, conditionals, variable assignment) and requires less boilerplate. The paper argues this explains the rise of tool-as-CLI over tool-as-MCP: a CLI is called from code, so the model can filter, transform, and compose outputs programmatically. An MCP tool is a single JSON call whose full result lands in the context window.

#### 4. Programmable Loop Engineering
Developers and models use ordinary Python to create subagents, call strategies, and write produce/evaluate/retry orchestration loops. The CodeAct system prompt documents the fan-out pattern (`@strategy`-decorated standalone functions run in parallel with `asyncio.gather`). No separate workflow language is needed.

#### 5. Explicit Object State
State lives on `self` and ordinary Python objects, rendered into a bounded per-turn state block that is re-evaluated on every LLM turn. The agent can store, inspect, and reuse explicit state without reconstructing it from a message transcript. Data fields only: attaching method-like callables to public attributes of `self` is blocked by design.

**Contrast with most agents:** The conversation history IS the state. As conversations get long and history is compacted, state can be lost.

#### 6. Model-Callable Harness APIs
Structured context blocks, per-turn dynamic context (skill/tool inventory blocks), and queryable session events are first-class runtime APIs shared by developers and the model. By default, `self.context` and `self.events` are omitted from the agent's self-documentation until the developer opts them into visibility per instance.

### Framework Comparison (Table 7 from the Paper)

The paper scores 14 agent frameworks against the six capabilities. **No other system combines all six, but most are adopting some of them:**

| System | Typed I/O | Pass by Ref | Code as Action | Loop Engineering | Object State | Harness APIs |
|--------|-----------|-------------|----------------|-----------------|-------------|-------------|
| **NOOA** | ✅ Strong | ✅ Strong | ✅ Strong | ✅ Strong | ✅ Strong | ✅ Strong |
| LangGraph / LangChain | 🟡 Partial | 🟡 Partial | 🟡 Partial | 🟡 Partial | 🟡 Partial | 🟡 Partial |

### Safety Considerations

⚠️ **NOOA agents can execute LLM-generated code.** Defense-in-depth:
- AST validation of generated code (safety validator screens cells for hazards: eval/exec, blocking calls, unbounded loops)
- Module deny-lists before execution
- These are **not containment boundaries** — they catch mistakes, not malicious code
- **Always run in a sandbox** (container, VM, or NVIDIA OpenShell)
- The paper is explicit: "NOOA's isolation philosophy is the same as any harness with a shell tool: sandboxing goes around the agent process. A shell tool is no safer than in-process Python."

### Future Directions (from the Paper)

1. **Agent optimization via agent rewriting:** Move beyond prompt search toward rewriting every part of the agent: prompts, docstrings, typed method signatures, helper code, tool descriptions, context policies, retry loops, decomposition structure. GEPA-style reflective optimization as starting point.

2. **Skills as full software packages:** Today's skills are text snippets or informal procedures. Expected to become full software libraries with typed APIs, documentation, tests, examples, subagents, dependencies, and versioned interfaces that agents can inspect, call, repair, and extend.

3. **RL to unlock inductive reasoning:** Outcome-driven RL (à la DeepSeek-R1) over complete agent trajectories could teach models to use harness APIs, dynamic context, pass-by-reference objects, and code-as-interface as a learned reasoning substrate. The harness becomes the action space in which agents learn to construct, test, and reuse problem-solving structure.

## Cross-Cutting Themes

### 1. Agent Orchestration Is the New Frontier
Four of the 10 repos (Skills, OmniRoute, Orca, NVIDIA OO-Agents) are about **how to run and coordinate agents**, not the models themselves. The tooling layer around AI is maturing rapidly.

### 2. Deterministic + LLM Hybrid Architectures Win
Both Alibaba's Open Code Review and NVIDIA's OO-Agents use the same pattern: **deterministic engineering handles structure**, LLM handles dynamic decisions. Pure prompt-driven approaches are consistently outperformed.

### 3. Paged Attention + KV Cache Management Is the Core Bottleneck
The vLLM deep dive makes clear that almost every optimization (prefix caching, chunked prefill, speculative decoding, disaggregated P/D) is ultimately about **managing KV cache memory more efficiently**. Understanding this subsystem is essential for anyone working with LLM inference.

### 4. Code as Action > Tool Schemas
NVIDIA's OO-Agents represents a philosophical shift: instead of defining JSON tool schemas, let the model write Python code against typed interfaces. More expressive, less boilerplate, but requires stronger sandboxing. The paper argues this explains why tool-as-CLI is beating tool-as-MCP — CLIs compose from code.

### 5. Agent Feedback Loops Matter More Than Prompts
Matt Pocock's skills framework codifies what experienced developers know: the biggest failure mode isn't bad prompts — it's **misalignment** and **lack of feedback loops** (tests, types, running code). `/grill-me` and `/tdd` are more valuable than any system prompt optimization.

### 6. The Field Is Converging on Six Agent Interface Patterns
NOOA's framework comparison (Table 7) reveals that 14 major frameworks are independently discovering the same six ideas: typed I/O, pass by reference, code as action, loop engineering, object state, and harness APIs. The newest capabilities from Microsoft, Pydantic, OpenAI, and Codex all shipped during NOOA's evaluation window. The convergence is accelerating.

### 7. MLA Changes the KV Cache Economics
The transformer math paper shows that MLA (DeepSeek V2) compresses the KV cache from `2 × N_heads × d_head` per token to just `d_L` (a shared latent dimension). Combined with vLLM's paged attention, this dramatically increases the number of requests that can be served concurrently — the core bottleneck identified in the vLLM deep dive.
